# Approved CV semantic search — checkpoint B

Contract frozen for interface review against checkpoint A commit650e40c; release capacity remains subject to measured acceptance. Migration reserved: `20261002210000_cv_search.sql`. The backend implements this contract; release capacity is finalized only after concurrent measurements.

This adds the exact retained text of approved CVs to semantic candidate search. Private draft CV text is deferred. Existing profile projections, keyword search and private-draft profile visibility remain unchanged. The complete semantic index moves to one measured MiniLM model namespace; profile and CV vectors are never mixed across models. CV text is available only with current `documents.download` permission and an active candidate's exact current active document. Text extracted from images is not represented; the UI must not imply OCR or exact eligibility filtering.

## Staff API and compatibility

Keep `/api/staff/profile-search`, staff MFA, mutation Origin checks, private/no-store responses, existing candidate read/write permissions and `TELEGRAM_INTAKE_ENABLED`.

Add optional `includeCv:boolean` to search, retryIndex and initial status filters. Omitted means false. The new UI offers **Include approved CV text**, on by default for new sessions when `cvAvailable:true`; otherwise it submits profile-only requests and displays no CV counts. Changing this option affects the next submitted query. `my_drafts` with includeCv:true is invalid400 because private CV search is outside this checkpoint. Requesting true without current documents.download returns403 before queueing or disclosing CV coverage. Do not silently downgrade a requested CV search.

- Search input `{action:"search",operationId,query,scope,readyOnly,includeCv?}`; response remains202 `{queryId,status:"queued",expiresAt}`. Normalize omitted includeCv to false in operation receipts, so old-client retries remain identical. The new flag is part of request identity.
- Initial GET adds `includeCv=true|false` and returns existing fields plus `{includeCv,cvAvailable,cvProjectionVersion,capacity}`. `cvAvailable` means permission to request the mode, not that all CVs were parsed or indexed. `capacity` is null for profile-only mode.
- Query GET retains the existing DTO and adds `{includeCv,cvAvailable,capacity}`. Query text stays out of URLs. Existing status enum remains `queued|running|completed|failed|cancelled|expired`. A cached CV query invalidated for access/content safety becomes failed, results[], nextAfter:null; the UI offers a fresh query with a fresh operationId. Old operationId replay never silently creates a different search.
- Retry input `{action:"retryIndex",scope,readyOnly,includeCv?}` keeps `{ok,retried,remainingFailed}`, counting at most100 eligible component jobs. With false it touches profiles only; with true it includes authorized profile/CV jobs. It never retries another recruiter's private source or a restricted document.
- Cancel, 15-minute query expiry, query priority and result pagination remain unchanged.

Result keeps `{sourceType,sourceId,sourceRevision,displayName,headline,location,hasCv,missingFields,score,matchedText,href}` and adds `matchedComponent:"profile"|"cv"`. `sourceRevision` identifies the winning component revision. A CV winner also has `matchedDocument:{id,filename}`; a profile winner has matchedDocument:null. Existing candidate href is retained; no object key or storage URL is exposed. matchedText remains <=500 characters, verbatim from the winning exact chunk, never model-generated. This is an excerpt of parsed text, not a claim that every image/page element was understood.

Exactly one result per candidate/draft, ranked by its maximum authorized ready chunk score. Ties within a candidate prefer profile, then lower chunk ordinal; candidates tie by the existing sourceType/sourceId order. Group BEFORE pagination and result persistence. All ranks are stored; no hidden top-N cap. Cursor stays query-bound and uses score/sourceType/sourceId, never component IDs.

## Coverage and bounded capacity

Within the new model namespace, profile-only counts, scores and ordering must remain identical, including for users without documents.download, before and after any CV indexing activity. The deliberate global model migration changes old E5 scores; it is not represented as numerical parity across models. They must not reveal the presence/count of CV text sources.

Coverage adds `fullyIndexed` and `cv` to existing `{eligible,indexed,pending,failed,retryable,corpusChanged}`. For profile-only, fullyIndexed=indexed and cv=null. For CV mode, top-level counts are distinct visible profiles: eligible has at least one selected source; indexed has at least one ready component; fullyIndexed has every selected component ready; pending/failed count profiles having a component in that state (they can overlap indexed). retryable remains the current number of retryable component jobs to match the bounded retry action. `cv` is `{attached,withoutRetainedText,eligible,indexed,pending,failed,retryable}`. Attached counts approved candidates with an active current CV; withoutRetainedText counts those lacking an eligible retained text artifact. The remaining fields count approved candidates with a currently eligible retained CV artifact. WithoutRetainedText does not distinguish a never-analyzed file from explicitly excluded text and must not expose another recruiter's private analysis decisions. A normal attached but unparsed/excluded CV is not falsely counted as an indexed text artifact. UI explicitly shows CV indexing progress and partial coverage, not “all CVs searched” merely because profile indexing finished. Query coverage is a scoring snapshot except retryable; growth sets corpusChanged.

CV mode includes every authorized ready profile/CV chunk or returns a terminal error; it never samples candidates, drops CV tails, substitutes a centroid, or returns a partial scan as complete. Before ranking, count selected ready chunks with current visibility. The compile-time CV-mode limit, `CV_SEARCH_MAX_READY_CHUNKS`, is finalized from the measured acceptance tiers before release; SQL independently enforces the same bound. No numeric production limit is assumed in this interface contract. `capacity` is `{readyChunks,maxReadyChunks,withinLimit}` and is owner/scope filtered, with no other-owner/private/document count leakage. Above the limit, fail `SEARCH_CAPACITY`, return no results, and explain that profile-only mode remains available. This is an explicit capacity limit on the entire selected corpus, not a truncation to the first N chunks. Existing profile-only capacity/deadline behavior is unchanged.

Before enabling this checkpoint, benchmark actual authorized query paths at10k/25k/50k/100k chunks with two concurrent query requests plus ongoing index publication. At the release limit, target p95 scoring below5seconds and first/subsequent pages below500ms, under the existing10second database scoring deadline. Document machine/resources/sample counts. Choose the largest actually passing measured tier that satisfies the margin, document its honest supported corpus size, and raise it only after a new passing measurement. If10k does not meet the gate, optimize or withhold release instead of assuming a safe floor. Do not present10k as a sufficient production target for all users; hundreds of long conversations may produce more chunks, and that workload must be sized before deployment. Beyond-capacity fixtures must return explicit errors. Any runtime timeout remains failed SEARCH_TIMEOUT with no results. Limits count chunks, never chats or candidates.

## Source components and namespaces

Add `component:'profile'|'cv'` to `app.profile_search_sources`, default profile for all existing rows. Replace uniqueness with `(source_type,source_id,component)`; preserve existing profile source IDs and invalidate their derived vector namespace as described below. Every existing profile invalidator/ON CONFLICT target explicitly uses component=profile. Draft CV source rows are prohibited by a database check.

CV source projectionVersion=`candidate-reviewed-cv-v1`; profile remains `candidate-profile-v1`. All components and queries use indexVersion=`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2@e8f8c211226b894fcb81acc59f3b34ba3efd5f42:mean-pool:l2:384:v1` with profile/query chunkerVersion=`minilm-utf8-128-v1` (token-packed) and CV chunkerVersion=`minilm-cv-lines-128-v1` (line-aware). This is 384-dimensional mean pooling with L2 normalization, no query/passage prefixes, and a maximum of128 tokens including special tokens. Query jobs retain the profile projectionVersion. The pinned tokenizer partitions exact text with preferred newline/paragraph boundaries and adaptive adjacent packing. Equal dimension does not make old E5 vectors compatible.

CV projection is exactly `candidate_reviewed_cv_text.text_content`, with no labels, normalization, whitespace collapse or summary truncation. SHA256 of those UTF8 bytes must equal the artifact text_sha256. Bind source to immutable reviewed-artifact ID, candidate ID, document ID, document SHA, text SHA and parser version. SourceRevision independently fences current publication. Text <=65,536 UTF8 bytes; complete existing tokenizer-aware partition, <=256 chunks, <=128 tokens including special tokens/16,384 bytes/16,000 codepoints each, <=8 embeddings per acknowledgement. No profile+CV concatenation that consumes either component's byte allowance.

Migration deletes all derived chunks/ranks, clears source manifests/stage receipts/leases, increments source revisions, and requeues every non-retired profile and eligible reviewed CV under the new namespace. Existing unexpired queries become failed INDEX_CHANGED with embeddings/receipts/results removed; their query text remains available for a fresh-operation rerun. Existing cancelled/expired queries remain closed. Worker-online timestamps reset. Candidate data, reviewed CV artifacts and source projections remain authoritative; source text is recomputed asynchronously on the Mac worker claim path. This reset is required because unchanged E5 CV fixtures failed the relevance gate while the pinned MiniLM model passed both original-profile and CV gates. No mixed vectors or score calibration is permitted. A component is searchable only after all its current chunks are acknowledged. Profile-only hits remain usable while a CV component is queued or failed. Unusual unchunkable legal text must fail explicitly, never silently omit bytes.

## Worker compatibility

Existing `/api/profile-search/worker/{claim,complete,fail}` and scoped bearer token remain. Claim accepts old `{}` for rolling compatibility, but it returns idle and does not update compatible-worker availability. All new query/profile work requires `minilm-v1`; CV work also requires `approved-cv-v1`. New workers send `{capabilities:["minilm-v1","approved-cv-v1"]}`; unique known capabilities only, at most2. New claims may receive CV stages only when the token owner's current documents.download permission and candidate permissions pass. A worker without document permission continues ordinary profile/query work. Host never sends private draft CV text or storage credentials.

Plan/embed jobs add `source.component` and use the component's projectionVersion. CV jobs add `source.document:{id,sha256}` and `source.reviewedTextId`; the supplied source.text and sha256 remain exact immutable server-owned projection. These identifiers are metadata, never client-controlled routing. Query jobs add no source and use the same new model namespace. Complete payload shape stays unchanged: its job ID, sourceRevision/SHA and projectionVersion bind the component and document; no user-supplied candidate/document IDs are accepted. Host rejects mismatched projectionVersion or chunkerVersion for the locked source component, not merely any version from an allowlist. Durable pending receipts replay both namespaces with existing idempotent fencing. The local model service and semantic worker must be upgraded together before compatible jobs can run. Old worker completion namespaces are rejected even when their vectors have384 dimensions.

A revoked document permission immediately prevents content-bearing plan/embed claim, completion and replay for CV components; it does not prevent profile completion. Invalidated current document/revision returns409, authorization revocation403. Failed CV jobs do not poison the profile job or block profile searches. Use current priority/fairness, five-attempt retry and visible errors.

## Access, mutation and cache safety

All new/changed tables keep forced RLS. CV source and chunk access additionally requires current documents.download and live exact candidate/current-document/reviewed-artifact binding. Denormalized component on chunks may avoid unnecessary joins for profile rows, but must be database-maintained from the source. No trusted client can choose profile to disguise CV bytes. Narrow definer entry points recheck permissions; explicitly revoke PUBLIC on every new wrapper/helper and verify staff/worker/maintenance grants. No direct table grants to runtime callers.

Canonical candidate lifecycle/current document, document lifecycle/blob eligibility, reviewed artifact insert/change/delete and merge adoption update the CV source under transactional source locks. Invalidating an existing component increments revision, clears its projection/chunks/receipts, fences leases and retires or requeues it. All real mutation paths (manual replacement, approval, privacy restriction/erasure, merge and authorized direct operations) must be covered, not only UI callbacks. Source projection and completion validate exact live binding even if an invalidation trigger has already run. Organization/source indexes keep worker claims bounded under large other-owner/private queues.

Separate CV **safety epoch** from ordinary **growth revision**. Safety epoch changes for removal, restriction, replacement, changed reviewed text/hash, or reassignment of an existing CV source. Publishing the first complete vector set for unchanged authorized text, adding a newly approved CV, retries and harmless backfill progress change only growth revision. Ordinary profile corpus revision remains separate so CV activity cannot change profile-only coverage.

A CV query captures permission mode and safety epoch with its coverage snapshot before ranking. Recheck both after ranking before finalization, and on every status/page/receipt path before exposing scores, snippets, coverage derived from CV sources, or cursor. Changed permission fails `CV_ACCESS_CHANGED`; changed safety epoch fails `CV_RESULTS_CHANGED`. Return results[], nextAfter:null, cv coverage:null and no cached CV counts on these failures. Current cvAvailable may be returned. No fallback that hides only the winning CV snippet while retaining its sensitive score/order. Fresh harmless publications leave cached results usable with corpusChanged:true; users can rerun when desired. Profile-only queries ignore all CV epochs. Query expiry and bounded physical result cleanup reuse existing maintenance.

Ranking uses one consistent statement snapshot of authorized eligible chunks. Growth during the scan produces a conservative coverage warning; security/content mutation before or after the scan is fenced by the safety epoch and final/page rechecks. Avoid holding organization-wide epoch locks during vector ranking; define deterministic write-lock order before implementation and test concurrent replacement/index/merge paths. A permission check may be hoisted once per authenticated statement, but current source identity/lifecycle is never inferred from client metadata.

## Merge preservation

Existing merge moves documents and adopts the source candidate's current CV only when the target has none. Its reviewed-text artifact currently remains bound to the merged candidate. Extend the actual merge transaction to transfer/rebind that exact reviewed row ONLY when that exact source current document is adopted by the target; preserve original reviewer/time/parser/hash/text. Lock source/target candidates in the existing deterministic order, record adoption before source current_document_id is cleared, move the artifact while existing document ownership is moved, then invalidate old CV source and queue target CV source. If target retains its own current CV, do not attach or index source text for the target. Do not reconstruct provenance by looking up an arbitrary artifact with the same document ID. Restriction/erasure retains its existing audited behavior and makes old text/vector/cached scores inaccessible immediately.
