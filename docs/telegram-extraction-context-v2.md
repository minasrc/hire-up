# Bounded Telegram extraction context

`TELEGRAM_EXTRACTION_CONTEXT_ENABLED=true` explicitly opts the host into v2 claims. It defaults off. Enable only after the operator accepts the additional retained private text sent to the already configured extraction provider and verifies model quality on authorized representative examples. No new provider or embedding calls are introduced. Deploy the v2 migration and host/worker code before enabling this flag. Disabling it pauses recovery of unfinished v2 jobs until reenabled; existing v1 work continues. Verified staff status includes `contextEnabled` and each listed job's `schemaVersion`, so unfinished v2 jobs can be labeled paused until an operator reenables context.

Capability lists must include v1; a v2-only list is rejected so disabling opt-in cannot return an unsupported version. New workers advertise `schemaVersions: ['candidate-extraction-v1', 'candidate-extraction-v2']` on claim. Old `{}` claims receive only v1. A new worker receiving an explicit HTTP400 on capability claim retries that claim once with `{}` and caches legacy mode until process restart. It does not fall back on authentication, conflict, throttling, server or network failures, or provider errors. Deploying host first remains recommended; restart a legacy-mode worker after host upgrade to negotiate v2. A capable opt-in claim upgrades only its newly leased snapshot: the original primary `messages` array remains byte-for-byte intact, with the existing 40-message and 48 KiB ordinary / 320 KiB legal singleton envelopes. A snapshot with no qualifying retained context, or a full singleton without room for it, stays v1 with its original digest and validation behavior. Source digest is recomputed over canonical PostgreSQL JSON; completion is fenced against its exact digest, role arrays and dependency ledger. Schema/prompt versions are paired v1/v1 or v2/v2. Original v1 receipts, including pending acknowledgements after retention, replay unchanged.

`source.contextOnly` contains at most eight full original retained message bodies and at most 8 KiB canonical JSON. Explicit reply ancestors take priority (maximum two links), followed by the nearest earlier retained messages. Context must belong to the same owner, organization, account and chat, and a strictly earlier retained extraction origin. Released, purged, unavailable, oversized and missing context is omitted. Missing context remains unknown. The bounded selection can omit useful context; it is not a complete conversation reconstruction. No primary text is truncated or primary quota increased to make room.

The v2 prompt describes context authors separately. Context can clarify a primary reply; it cannot create additional subjects, standalone candidate facts, sender attribution, identities or attachments. Both JavaScript and SQL validators accept quotes, identity message IDs and attachments only from primary `messages`. V2 additionally requires each normalized fact value to occur literally with deterministic conservative Unicode separator boundaries in a cited primary quote (ASCII case folding, exact non-ASCII case); this prevents a context-only value from being attached to a generic primary acknowledgement, and reduces paraphrasing and canonicalization. Unsupported aliases/codes must be omitted. It does not prove that the quote semantically supports the chosen field or identity. Exact quotes establish provenance, not semantic truth: recruiters retain review authority, and generated changes cannot overwrite human fields or approved facts.

The forced-RLS dependency ledger stores exact owner/chat/message/origin IDs and body digests, without another raw-text corpus. Runtime staff and worker roles cannot read it or invoke internal helpers. A real context-only edit, unavailable/deleted replacement, or physical maintenance deletion invalidates every dependent batch and fences leased completions, removes copied context and evidence, and preserves approved facts and human edits. Metadata-only `editedAt` changes do not churn jobs. Dependency origins are added to the existing retention graph: open review holds remain effective; origin release invalidates pending/completed dependent snapshots and removes their copied context before raw source deletion. Refresh keeps the original primary disposal origin, and purged source is never restored.

Verification uses synthetic local PostgreSQL17 and loopback provider fixtures only. It does not measure real-model accuracy. The flag is an operator content/quality acceptance gate, not a guarantee that extra context resolves ambiguous authorship.

Boundary matching pins Unicode16.0 punctuation/symbol/separator categories (P/S/Z), plus ASCII tab/newline whitespace U+0009..U+000D. JavaScript uses the same sorted intervals as native PostgreSQL17 integer multiranges; SQL does not use collation, ICU or extensions. Letters, all numeric categories, combining marks, format/control and unassigned characters are blocked as separators. This is more conservative than a runtime L/N regex, especially for combining marks and future Unicode additions. ASCII case folding and exact non-ASCII case remain unchanged. SQL nonempty separators fail closed outside a UTF8 database. Generation and exhaustive tests read the checksum-verified official Unicode16.0 source in `scripts/reference/unicode-16.0.0` rather than the engine’s Unicode/ICU data. See its README for provenance and license. Regenerate and verify with any Node22 release: `node scripts/generate-telegram-literal-boundaries.mjs` and `--check`; changing the pinned Unicode version requires a reviewed new migration and matching JavaScript data.
