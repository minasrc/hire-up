# Automatic extraction and reviewed-source lifecycle, version 1

This checkpoint adds automatic extraction catch-up for explicitly enabled chats, supports every currently legal imported message, and releases private source copies only after an explicit recruiter decision and all consumers have finished. Candidate approval alone never means that unrelated job, client or lead discussion was reviewed. Default: keep context. No model classification is authority to erase it.

## Existing staff extraction API

The existing `/api/staff/telegram-extraction` keeps its feature flag, staff MFA, candidates.read/write, owner privacy, Origin checks and private responses. New actions:

- `{action:"setExtraction",chats:[{chatId:UUID,expectedVersion:integer}],enabled:boolean}`; 1–50 distinct current-account or historical-account owned chat IDs, atomic version check. Returns `{ok:true,updated:integer,queued:integer}`. Enabling queues available unprocessed work; disabling stops new claims/automatic continuation after any already leased batch finishes. It does not cancel the Telegram import, discard sources or discard generated drafts. A queued/failed batch remains retained and can resume on re-enable (failed work still uses explicit Retry). The current history chat version increments when its extraction flag changes.
- Existing `{action:"enqueue",chatIds:[UUID]}` becomes the compatibility action that enables automatic extraction and starts catch-up. UI copy becomes “Start automatic extraction”; it must no longer imply a one-shot operation. Chats with any previously requested extraction job are backfilled as enabled so deployment does not silently stop previously requested catch-up.
- `{action:"sourceRetention",jobId:UUID,expectedSourceVersion:integer,mode:"keep"|"release_after_review"}` returns `{ok:true,sourceRetention:SourceRetention}`. Only completed batches are eligible. `release_after_review` is an explicit attestation that the recruiter reviewed the entire batch and no longer needs its remaining context, including job/client/lead/irrelevant material. It requests cleanup when candidate/proposal/CV holds close. `keep` withdraws a pending release; purged sources cannot be restored and return409. No bulk unbounded release.
- Existing `reviewBatch` remains a compatibility action for explicitly releasing a completed, fully reviewed batch; the UI uses the versioned action above.

History chat DTO adds `{extractionEnabled:boolean,extractionPending:boolean}`. Chat version is the existing `version`, not a new competing revision.

Extraction list job DTO adds `{extractionEnabled:boolean,sourceRetention:SourceRetention}`. Existing pagination remains50. Existing counts add `{contextKept,releasePending,purged}`. `needs_review` includes completed batches whose sources are kept or whose review consumers remain open. Each job retains its draft IDs, including links to approved drafts with late pending suggestions; closed drafts remain reachable through these links.

`SourceRetention = {version:integer,state:"kept"|"release_pending"|"purged",requestedAt:ISO|null,purgedAt:ISO|null,holds:{openDrafts:integer,pendingProposals:integer,activeCv:integer},canRelease:boolean,canKeep:boolean}`. The UI says “Keep context” by default and offers “Release after candidate review” adjacent to the full-source viewer. It displays hold counts and explains that approval/discard/proposal resolution completes an already requested release automatically. Zero-candidate batches use the same explicit full-context decision; they are never automatically classified as disposable.

`GET ?jobId=UUID` keeps job/schema/model metadata and adds `sourceRetention`; `source` is the unchanged immutable source while retained and `null` after purge. A purged source is an explicit reviewed/deleted state, not an empty import. No source body or raw quote appears in maintenance responses.

## Catch-up and maximum-message support

Post-import insertion marks only an enabled chat as needing extraction in the same transaction that accepts its page. It does not call a provider. A partial index over enabled/pending chats feeds an owner-scoped catch-up pass of at most10 chats before extraction claim. One unfinished extraction job per chat remains enforced. Completion continues only when the chat is enabled; a concurrent final import page cannot fall between “no more messages” and durable queue notification. Fair oldest-served ordering and bounded passes prevent one full-history chat starving others.

Normal batches remain <=40 messages and <=49,152 bytes of PostgreSQL canonical JSON (`source::text`). If the first unassigned legal history message does not fit, reserve exactly that one message in a singleton batch <=327,680 canonical JSON bytes. Current history records are capped307,200 bytes, and chat metadata is bounded, so every legal imported message fits the singleton envelope. Never truncate, skip or mark it processed on provider failure. Existing INPUT_TOO_LARGE blocked jobs can retry into this singleton path.

Worker claim DTO is otherwise unchanged and adds `sourceLimitBytes:49152|327680`. Source digest remains over the exact canonical immutable snapshot. Worker source validation and provider request serialization accept the singleton envelope with a separate bounded1MiB provider JSON request budget (escaping can expand text); provider responses retain their existing bounded limit. A provider context-window refusal remains an explicit failed job, never a partial or empty success. No new model output schema or model-based deletion classifier.

## Cleanup proof, replay and tombstones

Cleanup is at batch granularity (at most40 messages, or one singleton). A release request is necessary but not sufficient. All referenced drafts must be approved/discarded; no pending proposal from the batch may remain; no CV retrieval for the batch may be queued/leased/waiting. Unprocessed history and unfinished/failed extraction batches are never purge candidates. Referenced open drafts also preserve attachment hints for future retry even if the current CV job failed/cancelled.

A successful transaction removes raw history message bodies, the immutable job source snapshot, resolved proposal quotes, the batch's attachment hints, and orphaned evidence/link copies. Late evidence on an already approved draft is included: dismissing its final pending suggestion does not currently remove evidence links, so cleanup removes only links attributable to the purged batch and deletes evidence only after its last link disappears. Retained draft profiles, reviewed fields, canonical candidates, CV objects, subject identity ledger and completed receipts remain. Minimal non-content chat/account/message/document identifiers needed for idempotency and completed CV replay may remain; filename already part of an approved CV is reviewed profile metadata, not raw chat text.

`telegram_extraction_sources(chat_id,message_id,job_id)` becomes the durable ingestion tombstone ledger: drop only its foreign key to deletable raw history messages, retain the job/owner/chat constraints. History page admission and quota calculations exclude existing raw messages OR tombstones before counting/inserting, including a new page ID or explicit full-history replay. Tombstones never contain text/attachment filenames. Unique account-scoped chat identity already prevents cross-account message collisions.

Retain extraction source/result digests and receipt. Worker completion first authenticates and validates the bounded result envelope, then checks the exact completed receipt before trying to load/validate quotes against retained source. A matching completed result+metadata+source digest replays even after purge and a lost lease ACK; conflicting results remain409. A new/uncommitted result still receives full independent source/quote validation on host and SQL. History page receipts and completed CV upload receipts remain usable after purge without reimport, another upload or fabricated evidence.

Quota decrement uses the exact deleted raw rows' stored_bytes/count under the existing owner quota lock. Repeating cleanup subtracts nothing twice. Released storage allows a recruiter to resume an explicitly capacity-paused import; cleanup does not silently resume imports.

## Locking and hosted maintenance seam

Existing owner quota rows serialize import/extraction/source deletion. Cleanup uses: owner quota → extraction job FOR NO KEY UPDATE → referenced drafts in UUID order → proposals/CV/evidence rows → raw rows/quota decrement. Consumer locks are NOWAIT or SKIP LOCKED; a busy consumer defers the batch, never waits while holding a queue lock. NO KEY UPDATE preserves concurrent foreign-key key-share compatibility. New CV creation/retry requires an open draft and rechecks retained source after locking that draft; cleanup cannot race a new consumer into a deleted snapshot. Proposal resolution already locks draft before proposal; cleanup takes the same order. Source lifecycle events only mark maintenance work due; they do not do heavy deletion inside approval or provider completion.

A small internal owner maintenance queue contains only organization/owner IDs and due time, with a narrowly internal global lookup policy. Source release/consumer decisions and search-query expiry schedule this queue. Before marking an owner asleep, maintenance rereads pending work under the queue lock so a concurrent event cannot lose a wake-up. Source batches have due/served metadata so held batches do not starve eligible releases. New events advance due time; held batches are reconsidered later even if the Mac stays offline.

Dedicated NOLOGIN role `app_telegram_maintenance` receives EXECUTE only on `app.telegram_maintenance_v1(p_limit integer default10) returns jsonb`; p_limit is restricted1–10 owner scopes. It cannot select tables, choose an owner, read source content, call staff/worker functions or invoke helpers. The security-definer routine derives actor/org context only from its internal queue, validates an existing explicit release plus all live holds, and may expire private search queries according to their established TTL. Previously authorized source disposal still completes if a recruiter later loses membership; no new extraction/provider access is granted.

Return `{ownersProcessed:integer,batchesPurged:integer,messagesPurged:integer,bytesFreed:integer,queriesExpired:integer,queryResultRowsDeleted:integer,remainingWork:boolean}`. Each call processes at most5 released batches per owner (50 total/2,000 raw messages max), with a10s statement timeout set by the host before execution. Busy rows defer safely; a failed transaction is fully retryable. Search expiry clears at most100 query text/vector rows and5,000 cached result rows per invocation, with indexed eventual continuation. Each owner can consume the remaining global query/result budget. A run that makes progress reschedules outstanding due work immediately, behind older due owners; owners skipped because the global budget is exhausted keep their earlier place, while genuinely busy/no-progress work backs off one minute. Held source batches wait until their next hold check or a consumer-resolution event. Explicit NULL or out-of-range limits are rejected. Targeted query reads always enforce expiresAt even before physical cleanup reaches that row. Expired queries are immediately unusable; no result page is served merely because physical deletion is pending. Minimal non-content receipts remain as already documented. Limits and queue indexes make the work bounded, without claiming physical cleanup happens before a successful scheduled run.

Root owns the authenticated hosted maintenance route, dedicated database credential wiring, request authentication,15-minute external scheduler/manual dispatch and runbook. This scheduler is independent of the personal Mac and keeps working when the intake feature flag is off. Deploying/configuring it requires the normal production release authorization; this checkpoint authorizes implementation/tests only. Backend owns migration20261002190000 and the narrow maintenance function; no storage deletion or general administrative API is added here.

## Parallel seams and verification

Backend: schema/leases/queue/retention DTOs, history tombstone admission, catch-up, complete-receipt-before-source-validation, maintenance proof and DB tests. Worker: singleton source limits/provider serialization and encrypted durable result replay against the same completion API. UI: chat automatic-extraction controls, explicit full-batch retention decision, live hold counts, purged-source display and closed-draft suggestion links. Root: hosted scheduler, credentials/runbook, actual worker/history/approval/maintenance acceptance.

Required scenarios: final-page/import-versus-completion catch-up race; enable/disable/re-enable and another owner's isolation; maximum legal singleton record without dropped bytes; provider failure leaves source unprocessed; shared draft/late approved proposal/CV holds block purge; explicit zero-candidate release; no model-inferred erasure of mixed context; repeat cleanup exact quotas; receipt replay after snapshot removal; repeated history page/new-page replay cannot resurrect tombstoned messages; active consumer race defers cleanly; bounded maintenance works with Mac offline, feature disabled and inactive former owner; no scheduler result exposes PII.
