# Retained Telegram conversation context

## Audit and implementation status

The original integration was incomplete for conversation context. At the audited main revision `86ab8b9345fcdd717953caff3cd5d7c04744c705`, Telegram account connection, selected-chat history import/resume, new-message sync, candidate extraction/review, CV processing and candidate/CV search existed. Original conversations had no searchable reader, candidate approvals lost precise message anchors, edits/deletions could leave derived proposals stale, and the scheduled maintenance run silently skipped because its endpoint/secret were absent.

The implementation adds owner-private conversation search and source navigation, durable candidate provenance, source-change invalidation and automatic refresh, native account/channel recovery with retained-ID repair, default-off bounded contextual extraction, and explicit maintenance configuration failure. The independent maintenance fix is merged in [PR #18](https://github.com/minasrc/hire-up/pull/18); the integration is published in [PR #19](https://github.com/minasrc/hire-up/pull/19). Check those release records for the current merge, CI and deployment status. Publishing code is not a claim that production setup or real-account acceptance is complete.

Release priorities are: (1) complete green CI and verify the automatic app/database rollout, (2) configure maintenance and verify real cleanup, (3) upgrade the Mac connector and accept real-account import/search/source freshness, (4) accept opt-in contextual extraction against permitted representative data, and (5) consider conversational semantic retrieval only after its authorization, relevance and retention design is settled. Manual acceptance and setup are listed below.

The history importer stores original text and attachment metadata. This workflow makes retained messages searchable and opens surrounding messages and reply targets, including imports from a disconnected account. It does not download attachments or interpret client requirements as candidate facts.

## Search and access

`/staff/telegram-intake/context` uses PostgreSQL 17 full-text search with the `simple` configuration and a GIN index on the retained source table. A dedicated non-login, non-bypass, SELECT-only role owns the internal search helper: the query predicate lives inside its owner/organization RLS policy so PostgreSQL can use the native GIN operator. Staff and connector roles cannot execute this helper or assume its role; the public staff operation verifies permission before invoking it. This avoids marking a function leakproof or bypassing access policies. Search supports words, quoted phrases, `OR`, exclusions alongside a positive term, exact sender usernames, a selected chat, inclusive UTC dates, and attachment metadata filtering. Results are newest first, with stable keyset pagination. This is lexical search: it does not provide stemming, accent folding, semantic similarity, or word segmentation for continuous Chinese/Japanese text.

Read access requires verified staff/MFA, `candidates.read`, the existing Telegram feature flag, and owner/organization RLS. Imported conversations remain private to their importer. Search terms use POST bodies, remain in page memory, and do not appear in the browser URL or local storage. Conversation links contain only chat/message identifiers. Requests and responses use private no-store; revoked access clears displayed source data. The client cancels obsolete reads and rejects responses from a previous authentication epoch.

Source text is kept intact; result cards show bounded excerpts, and the viewer shows the original retained message. Sender attribution, forwarded attribution, timestamps, reply links, and attachment metadata are displayed separately. Attachment entries explicitly say metadata only. A missing or unavailable anchor shows an honest explanation and any remaining neighboring messages.

Search coverage reports all retained source records owned by the requester, including unavailable placeholders. It does not mean every Telegram message is retained, or that all retained messages matched the filters. Releasing source through the existing retention workflow removes those rows and their search index entries together; there is no second permanent raw-text corpus.

## Freshness

New-message synchronization and retained-message reconciliation are separate lanes of the Mac connector. Reconciliation rereads a bounded set of retained IDs, advances a durable per-chat cursor, and fairly rotates selected chats. It requires the connected original account and current selection/connection leases. Explicit provider `MessageEmpty` becomes unavailable; an omitted response, failed access, or network failure is never treated as confirmed deletion. Purged rows are never reinserted.

The connector now keeps durable account update state and recovers edits/deletions with Telegram `getDifference`; selected channels use a separate channel update state and `getChannelDifference`. Update state advances only in the transaction that commits selected retained source changes. Encrypted pending acknowledgements survive a restart or lost response, and leases fence stale account/selection work. Explicit provider deletion is distinct from a missing message; omissions never imply deletion. Initial baseline and provider gaps request retained-history repair. Each connected work turn has a bounded provider request budget, shared fairly with history and CV work.

The UI distinguishes native recovery from repair progress, a last checked batch from a completed sweep, and offline, reconnect, paused/cancelled, waiting and scheduled states. Repair is eventual: four IDs per provider operation, shared with other lanes, means a 200,000-message import can take at least roughly 84 hours to sweep through. Native recovery is the primary path for prompt changes; Telegram waits, disconnected accounts and sleeping Macs extend delay. A native checkpoint does not prove every historical message was imported or every candidate extracted.

Changed source invalidates dependent machine proposals, copied quotations, attachment hints and in-flight extraction/CV work under a transaction. Human edits and approved candidate values remain authoritative. Source identity tombstones remain, while retention can still erase actual source rows and free quota. Automatic refresh must preserve original disposal intent and process only still-retained, permitted source; its dedicated regression suite is the release gate.

Candidate detail pages expose durable, private source-message anchors captured from exact candidate evidence. The anchors retain no copied text and follow candidate merges. A changed source warns that approved facts need human review; missing source opens the remaining conversation with an unavailable explanation. The source remains private to its importing owner, even when a candidate is shared with colleagues.

## Deployment and validation

Apply database changes before deploying readers, and keep `TELEGRAM_INTAKE_ENABLED` disabled during rollout until acceptance passes. The search migration rewrites existing source rows to add a generated vector, backfills timestamps with the privileged migration operator (the owner role has forced RLS), then creates indexes. It is atomic, with a 2-second lock wait and a 30-second deadline per statement. These deadlines deliberately abort instead of holding a production table indefinitely. The migration operator must satisfy the existing portable PostgreSQL role contract and bypass forced RLS during the global backfill.

The integration adds nine ordered migrations, `20261011120000` through `20261011200000`: source search, retained-ID reconciliation, automatic refresh, candidate provenance, native account state, native channel state, RLS-compatible GIN retrieval, opt-in extraction context, and deterministic multilingual literal validation. Use the existing migration workflow in order; do not enable the readers or connector protocol against a partially applied set. Verify the additional non-login index role and internal helper privileges as part of the staging rehearsal. Host/worker version negotiation preserves old extraction claims while the connector is upgraded; restart a worker that entered legacy mode after upgrading its host.

A 200,000-row disposable test is available as `node tests/database/telegram-context-scale.mjs`; it records rewrite/index timings and query plans and fails unless the private search helper actually uses GIN. A local corpus held 141,090,895 source bytes (about 134.6 MiB). Across runs the search migration took about 38–55 seconds total, with each statement within its separate 30-second limit. The final rare-term GIN plan returned 200 matching rows in about 16.7 ms SQL execution; the complete page operation took about 1.53 seconds including disposable-process/authentication overhead. Maintained quota coverage avoided a full-history count. These results cover this synthetic corpus only. Local timing does not establish production capacity or a production latency SLO. Before a populated rollout, rehearse against a sanitized representative corpus. If lock or statement deadlines abort, confirm the migration rolled back and remains unapplied. Use a planned maintenance window and an explicitly reviewed deployment change for a larger corpus; do not silently increase timeouts in the application or report a partially indexed corpus as complete.

## Remaining operational acceptance

These actions require the account/repository operator and must not be represented as completed by synthetic tests:

1. Verify all nine migrations and the hosted deployment through the normal release workflows, then install the compatible Mac connector. Credential setup, a populated production-capacity rehearsal and account acceptance remain operator responsibilities.
2. Configure the existing Telegram maintenance URL and bearer secret in the scheduler and the matching hosted maintenance/runtime credentials. Missing configuration must fail the scheduled run. Confirm real cleanup totals and backlog are recorded after an explicit source release; the audited workflow previously skipped every request because these secrets were absent.
3. Complete real-account QR/2FA, selected-chat import, restart/resume, new-message sync, direct/group/channel edits and explicit deletions, offline gap repair, candidate review, approved profile/CV search, and source release in a permitted test conversation. Simulate lost acknowledgement and connector restart; verify no duplicates, missed committed update state or source resurrection. Confirm membership revocation and mobile use against the deployed app. Never use a production recruiter account as an implicit test fixture.
4. Establish authorization for the Telegram content processing being enabled. Broad AI processing/indexing must satisfy Telegram's current content terms and applicable participant authorization; account ownership alone must not be assumed sufficient. See the official [content licensing terms](https://telegram.org/tos/content-licensing).
5. Test the actual configured extraction/embedding models with representative, permitted multilingual conversations and ambiguous/forwarded candidate descriptions; synthetic provider responses do not measure real model quality.

For step 2, the GitHub Actions secrets are `TELEGRAM_MAINTENANCE_URL` (HTTPS, ending in `/api/telegram-maintenance`) and `TELEGRAM_MAINTENANCE_SECRET`. Neither repository secret was configured at the release audit. The host needs the matching secret and server-only `TELEGRAM_MAINTENANCE_DATABASE_URL` for a dedicated `NOINHERIT` login with only `app_telegram_maintenance` membership. Follow the existing [retention release procedure](telegram-retention-release.md), together with the merged maintenance-health patch; never reuse a staff/owner database login or commit credentials. Once configuration is complete and a production cleanup run is explicitly approved, dispatch the workflow once, verify its aggregate response, then confirm the hourly schedule actually runs. Cleanup can permanently purge source already released by recruiters.

The current semantic profile/CV search is a separate feature. Full conversational semantic retrieval and structured extraction of non-candidate client/project context need their own scoped data/consent and retrieval design, relevance evaluation, and retention boundaries. Keep the original-message search available as the auditable source while those capabilities are designed.

## Further code priorities

Bounded contextual extraction is implemented behind `TELEGRAM_EXTRACTION_CONTEXT_ENABLED=true` (default off). It adds at most eight retained messages / 8 KiB, prioritizes two-hop replies, preserves primary batching and source limits, and negotiates a distinct schema/prompt version. Context authors and attachment metadata remain separate from primary evidence and CV actions. Exact dependency IDs/digests fence source changes, including physical maintenance deletion; source release clears copied context and refresh preserves original disposal intent. When no context fits, the original v1 snapshot remains intact.

Version 2 requires primary-only quotations/identities/attachments and literal primary support for fact values. This intentionally limits paraphrasing and canonicalization; it does not establish semantic truth or eliminate ambiguous authorship. Keep it off until permitted real-model acceptance compares quality and false attribution against v1, including negation, contradictions, forwarded authors, generic replies and prompt injection. See [the v2 contract](telegram-extraction-context-v2.md) and [the nine-case evaluation procedure](telegram-context-evaluation.md). The default evaluator runs offline and explicitly reports that model quality is unmeasured; real-provider mode needs an explicit command and permitted synthetic test configuration. Disabling the flag pauses unfinished v2 recovery; compatible v1 work continues. The queue identifies this configuration pause.

If conversational semantic retrieval is required beyond the delivered keyword/phrase search, build a versioned, disposable passage index keyed by account/chat/message/revision with source anchors, rather than embedding entire histories as one document or raising the existing CV search scan cap. Use lexical retrieval as a baseline, combine scores with measured relevance, filter access before ranking, and delete derived passages atomically with source disposal. Establish language-specific evaluation and a supported scale envelope before making semantic coverage claims.
