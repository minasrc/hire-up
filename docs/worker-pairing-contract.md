# Browser-first Mac worker pairing — frozen interface

Frozen against checkpoint2eecd8b under the user-authorized continuation. Reserved migration:20261002220000_worker_pairing.sql. This commit specifies the shared interface only; backend implementation starts on parent go-ahead. Phase1 covers pairing, own-device list, revoke and explicit same-token renewal. Unified launcher/service setup is a separate slice.

## Flow and boundaries

1. On the existing Connect Telegram page, an MFA-authenticated recruiter selects **Pair this Mac**. The browser creates a cryptographically random invitation secret and asks the host to create an invitation bound to the current recruiter/workspace.
2. The browser shows an enrollment value for a local pairing command's hidden stdin prompt. No invitation or credential appears in a URL, command argument, generated shell command or log. The Mac command receives only a validated HTTPS server origin as a nonsecret argument.
3. The Mac durably creates its worker token and independent poll verifier, submits their hashes with the invitation proof, and displays its device name/fingerprint. The browser shows the submitted fingerprint and requires **Confirm device**. No automatic approval.
4. The Mac polls with its verifier. Approval returns worker UUID/name/expiry, never a credential. The Mac retains its original token, saves the UUID, and uses the existing worker protocol. The browser never sees the worker token or poll verifier.

No unauthenticated start endpoint creates records. Knowing a pairing UUID cannot claim or inspect it. The invitation is already owner/workspace-bound; another MFA user cannot approve or rebind it. A stolen invitation can at most submit a different pending fingerprint before the Mac; browser confirmation is therefore necessary. Pairing does not log in to Telegram or prove that parsing, provider or model services are ready.

## Secrets and local persistence

- Browser invitation secret:32 CSPRNG bytes,43-character unpadded base64url. It stays only in browser memory until handed to the Mac. Host receives `SHA256(UTF8(secret))`; it never stores or returns the plaintext. Copying this limited, ten-minute invitation is permitted; it is not a worker credential.
- Mac worker token: preserve current `randomBytes(48).toString('base64url')`, exactly64characters. The host hash is SHA256 of the UTF8 credential string, matching `telegram_worker_context_v1`, not the decoded48bytes.
- Mac poll verifier: independent32random bytes,43base64url characters, stored before network I/O. The host stores its SHA256 hash; the raw value is used only in the poll Authorization header.
- Before claim, atomically persist `{version:1,serverOrigin,pairingId,claimId,workerToken,pollVerifier,deviceName}` under a0700 user-owned directory/0600 nonsymlink file. Never overwrite an existing configured worker or pending pairing without an explicit local choice. Reuse these exact values after uncertain ACKs/restarts.
- Fingerprint: first12hex characters of SHA256 over canonical JSON `["worker-pairing-v1",pairingId,claimId,tokenSha256,verifierSha256]`. Both host and Mac compute it. It is a visual matching aid, not another bearer secret.
- Existing vaults remain unchanged: connector scope is server origin+worker UUID; history/CV add account/connection scopes; extraction/CV-analysis/semantic receipts derive scopes from the worker token. Pairing and renewal never rotate that token or UUID implicitly.

## Staff API — existing staff pool, MFA and Origin guard

`/api/staff/worker-devices`, private/no-store. Existing `TELEGRAM_INTAKE_ENABLED`; candidates.read/write required. Actor/org always come from `staffApiContext` and `withStaffTransaction`, never body fields. Body limit2048bytes, exact field allowlists, names1–80 valid Unicode characters without controls. Operation UUIDs bind exact normalized request digests; changed replay409. Per-action receipts are bounded as specified below. Responses below are bare JSON.

- POST `{action:"invite",operationId,invitationSha256,name}` →201 `{pairingId,status:"invited",name,expiresAt}`. TTL10minutes from first commit; exact replay returns same record/expiry. Browser constructs the stdin value `pairingId.secret`. If response is lost, browser retries with its same in-memory secret/hash/operationId. If browser memory is lost before copying, cancel and create a new invitation; host cannot recover the secret. Unique invitation hash, no plaintext persistence.
- GET `?pairingId=UUID` → `{pairingId,status,name,deviceName:null|string,expiresAt,deviceFingerprint:null|string,worker:null|{id,name,expiresAt},organization:{id,name}}`. Own invitation only; other owner/org404. Status is `invited|claimed|approved|cancelled|expired`. Expiry checked on every request, not just by a cleanup job. Claimed is not yet authorized to perform worker operations.
- POST `{action:"approve",operationId,pairingId,deviceFingerprint}` → `{pairingId,status:"approved",worker:{id,name,expiresAt}}`. Only `claimed`, unexpired and exact fingerprint; current owner/workspace and current permissions rechecked. Atomically insert original token hash into `telegram_workers` and save the worker FK on invitation. Expiry defaults to existing30days. Exact same-operation approval replay returns its fixed original receipt; a fresh operationId on an already-approved pairing returns409 PAIRING_DECIDED and the UI refreshes status, with no new receipt allocation. No second worker on retries. Concurrent approval/cancel serializes on pairing row; only one final outcome.
- POST `{action:"cancel",operationId,pairingId}` → `{pairingId,status:"cancelled"}` for own invited/claimed row. Exact cancellation replay returns its original receipt; a fresh cancellation of cancelled/expired/approved state returns409 PAIRING_DECIDED, directing an approved device to revoke. No remote token/secret deletion claims.
- GET without pairingId: own devices, newest-first `(created_at DESC,id DESC)` keyset pages25; `{devices:[{id,name,createdAt,expiresAt,revokedAt,lastSeenAt,connectorLastSeenAt,compatibleSearchLastSeenAt}],nextAfter,organization:{id,name},pairings:[{pairingId,status,name,deviceName,expiresAt,deviceFingerprint}]}`. Pairings contains at most the owner's2live invitations, allowing refresh/resume/cancel after browser memory is lost; it never returns the invitation secret. No hashes, keys, credentials or other-owner rows. Existing RSA heartbeat90second activity and compatible semantic claim timestamps remain distinct. Do not label generic activity “all services ready.”
- Revoke uses existing DELETE `/api/staff/telegram-intake/workers/:id`; expose it in the list. Preserve compatibility and its owner scope. Repeated revoke of an own record is harmless. Do not change legacy registration limits/contract in this slice.
- POST `{action:"renew",operationId,workerId,expectedExpiresAt}` → `{worker:{id,name,expiresAt}}`. Small explicit MFA-owner action only when an unrevoked worker is within7days of expiry or expired within the last7days. Require expectedExpiresAt to equal the current stored timestamp; set expiry exactly now+30days, never beyond that horizon. Exact latest-operation replay returns its original receipt before checking the expected timestamp; an older operation after a subsequent renewal fails409 WORKER_CHANGED. Store only the latest renewal operation/digest/receipt on the worker. Current membership/candidate permissions required. Never renew revoked credentials or rotate token/worker UUID. Older expired devices require new pairing and a new local namespace, with old local evidence preserved for explicit cleanup. UI explains that renewal preserves existing device access; it is never a side effect of polling or activity.

Browser refresh can resume the claimed/approved invitation by ID in nonsecret page state; it cannot redisplay a lost invitation secret. Display workspace and requested device name next to fingerprint confirmation. No pairing-secret query parameter or auto-approval on navigation.

## Outbound Mac API — proof-gated public requests

`POST /api/worker-pairing/{claim,poll}`. Reject Origin and cross-site fetch metadata; HTTPS canonical origin only (HTTP loopback test-only), no redirects, no cookies/CORS. JSON2048byte cap, private/no-store, no-referrer, fixed redacted error codes. Ten-second client deadline. No record creation from these endpoints.

- Claim Authorization `PairingInvite <43-character secret>`; body `{pairingId,claimId,deviceName,tokenSha256,verifierSha256}`. Hashes lowercase64hex. SQL compares invitation proof, pending expiry and stored owner membership/permissions before accepting. Response200 `{pairingId,status:"claimed",deviceFingerprint,expiresAt,pollIntervalSeconds:5}`. `invited` becomes `claimed` once; deviceName is the submitted Mac label shown for confirmation and stored separately. The original invitation name remains the worker name, so claim cannot alter the invitation receipt. Exact claim digest replay returns same fingerprint and expiry; same invitation with another claim/body409. Existing/elsewhere-reserved token hash is rejected without revealing its owner. No actor/org accepted. An already-approved exact replay can return only its pairing status; use verifier-authenticated poll for worker metadata.
- Poll Authorization `PairingPoll <43-character verifier>`; body `{pairingId}`. Valid claimed proof returns200 `{status:"claimed",expiresAt,retryAfterSeconds:5}`; approved returns `{status:"approved",worker:{id,name,expiresAt},organization:{id,name}}`. Only metadata, never credentials. Unknown ID/wrong proof both404 `PAIRING_UNAVAILABLE`. Cancelled/expired valid proof returns terminal status without worker metadata. Approved poll rechecks worker revocation/expiry and current membership/permissions; revoked/unauthorized returns terminal `access_denied` with no saved approval metadata. Repeated approved replies reconcile lost ACKs for24hours after approval; afterward use worker APIs with the locally saved token.

After a successful claim the Mac clears the invitation secret from durable state; claimId/token/verifier suffice to continue polling. If claim response is uncertain, retain the invitation secret encrypted or in the protected pending file until poll proves the same claim exists. If neither verifier poll nor exact claim can recover before expiry, stop and request a fresh invitation; do not regenerate secrets into the same claim.

Final approved response must be atomically saved as the exact local credential JSON `{version:1,server,workerId,token,name,expiresAt,organization:{id,name}}` before deleting pending verifier state. Here server is the canonical origin and token is the original local64-character credential. Prefer a shared0600 credential file referenced by existing services. Add connector token-file input compatibility if needed, preserving current env/config options. Pair command does not modify Telegram API credentials, provider/model configuration, existing vaults, launch agents or service processes. Unified setup/launcher is deferred.

## Durable bounds with no IP configuration or HMAC secret

Use one reusable global public rate row holding the current minute and capped request count and existing owner IDs for invitation counters. Do not insert rate rows keyed by attacker-chosen pairing IDs, tokens, IPs or hashes. The public helper charges the global budget BEFORE any pairing lookup, including malformed/unknown proof attempts. Limit600requests/minute globally; global bucket updates atomic, rejected attempts return429+Retry-After. A wrong proof cannot mutate the target invitation's polling schedule, consume its claim, cancel it or lock it permanently.

Additional database bounds: <=2live invited/claimed rows perowner, <=10new invitations/owner/hour, <=1000live invitations globally. Owner counters are created only after MFA staff authorization and keyed by existing membership; fixed counter fields, no unbounded window rows. Exact invitation replay does not consume new-invitation budget. Valid polls no more than once/5seconds per invitation; faster requests429 without altering expiry. Per-row poll timestamp updates require matching verifier. TTL never slides. Use a short in-memory limiter only as an optional early optimization, never as the durable guarantee.

Global budget can throttle legitimate users during abuse; expose explicit retry timing and document it as bounded demo availability, not bot-proof service. Existing hosting-edge/WAF limits may supplement it but are not required secrets/config for this slice. Body read deadline and2048byte streamed bound apply before database work, avoiding large/slow unauthenticated bodies. Public pool max2, DB statement_timeout2seconds and lock_timeout500ms. No public record allocation, attacker-grown counter map or expensive source/profile queries.

Scheduled existing maintenance expires/deletes <=100pairing rows per call; terminal/replay receipts retained24hours, then remove invitation/verifier/token hashes from pairing rows. Active worker token hash remains in the existing worker table. Pending expired rows are inaccessible immediately even if physical cleanup is delayed. Retain compact nonsecret actor/org/worker/action audit identifiers only. No Mac-online dependency or new scheduled job required; add aggregate pairingRowsPurged to existing maintenance output if needed.

## Roles and locking: recommendation and deployment tradeoff

Deployment choice: create NOLOGIN NOINHERIT `app_worker_pairing`, and grant it to the existing NOLOGIN NOINHERIT `app_telegram_worker` group with membership `INHERIT FALSE, SET TRUE` (no ADMIN option). Existing hosted login→worker membership must retain SET TRUE. PostgreSQL17 permits SET ROLE through that membership chain even with inheritance disabled; migration/ACL tests must verify this using a synthetic NOINHERIT login with only existing worker-group membership. Public transactions explicitly SET LOCAL ROLE app_worker_pairing, never app_staff/app_executor. Reuse TELEGRAM_WORKER_DATABASE_URL with a separate max2 public pool, so no new hosted secret or login-name discovery is needed. This limits the active request's execution privileges; it does not pretend to isolate a fully compromised host login, which can still SET ROLE app_telegram_worker. A dedicated pairing-only login remains a future hardening option, not a deployment requirement.

Grant pairing role EXECUTE only on proof-gated claim/poll procedures and fixed budget admission; no tables, staff functions, generic worker-token functions or arbitrary actor/org setters. Every helper SECURITY DEFINER has fixed search_path and PUBLIC revoked. Registration helper accepts only a locked approved invitation and has no runtime EXECUTE. Staff role gets invite/status/approve/cancel/list/renew only. Existing worker APIs keep their token-based authorization and document permissions.
Use forced RLS for new tables; only narrowly owned proof-checking functions may locate unscoped pending rows. Runtime callers get no direct table access. Staff status/list always derive current actor/org and restrict owner. Existing broad token-lookup worker policy must not become an invitation-list mechanism. ACL regression must cover PUBLIC, staff, worker, pairing and maintenance roles with forged GUCs.

Lock order: rate bucket/counter first, then current membership authorization without org-wide UPDATE, then pairing row, then new worker insertion. Staff invite/approve/cancel take the fixed global enrollment row before locking a pairing, so the approval binding cannot change between public poll snapshots. Approval and renewal do not take an existing worker row followed by pairing row. Poll checks pairing proof without holding pairing UPDATE while acquiring the existing worker_context lock; lock worker first if a state recheck requires both, then pairing and revalidate binding. Avoid adding a pairing↔worker cycle to existing worker-before-org-share locking. Unique token hash + unique pairing.worker_id + operation receipt prevent duplicate registration.

## Expiry/revoke semantics and acceptance

Revoke/expiry stop host access immediately through existing worker context, including queued job completion. They do not guarantee Telegram logout or remote deletion of local files. Normal decommission uses the existing disconnect/logout acknowledgement before revoke; emergency revoke remains immediate with honest UI copy. Never mark Telegram disconnected without proof. Renew the same token/UUID to preserve pending encrypted receipts; no automatic rotation in this slice.

Acceptance: owner-bound invitation/create replay; claimant race and mismatched fingerprint; lost claim/approve/final ACK; valid/verifier poll after permission revoke; TTL and renewal horizon/replay; wrong proof leaves legitimate flow usable; global rate/owner invitation limits across independent app instances; no attacker-keyed counter growth; direct-role ACL failures; secret-free browser/log responses except the intentional one-time invitation handoff;0600/symlink/restart safety; paired token performs existing heartbeat and appears in QR-connect UI; old registration/API and worker vaults remain compatible. No live Telegram/provider calls are needed. Parent coordinates the milestone and authorizes implementation under the existing user request; no additional user approval gate is introduced.


## Exact response, pagination and receipt conventions

Bare successes only; no `{result:...}` wrapper. Staff mutations other than first invite return200. Invite first creation201/exact replay200. GET device list accepts only `after` (optional), with25items and nextAfter:null at the end. Cursor is unpadded base64url UTF8 JSON `{createdAt,id}` (<=256characters), strict UUID and valid timestamp; staff scope is independently rechecked and never taken from the cursor. Pairing status GET accepts only pairingId and cannot be combined with after. All timestamps are ISO8601; clients echo expiresAt unchanged for renewal's expectedExpiresAt. Device/worker names are plain text, never HTML. Organization display name strips control characters and is limited to200 Unicode codepoints, falling back to 'Workspace' if empty; its UUID remains exact. All consumers use the same bounded display metadata.

All new-route failures are flat `{error:fixedText,code,retryAfterSeconds?}` with no nested error object or sensitive detail. UI/CLI branch on code, not text. Fixed mappings:

|HTTP|code|fixedText|
|---|---|---|
|400|INVALID_INPUT|Check the request fields.|
|401|UNAUTHORIZED|Sign in to continue.|
|403|FORBIDDEN|This action is not permitted.|
|403|INVALID_ORIGIN|This request origin is not permitted.|
|404|PAIRING_UNAVAILABLE|Pairing is unavailable or has expired.|
|404|WORKER_UNAVAILABLE|This device is unavailable.|
|409|OPERATION_CONFLICT|This operation was already used for a different request.|
|409|PAIRING_CLAIMED|This invitation was already claimed.|
|409|PAIRING_DECIDED|This pairing is already closed. Refresh its status.|
|409|WORKER_CHANGED|The device changed. Refresh before trying again.|
|409|RENEWAL_UNAVAILABLE|This device cannot be renewed now.|
|409|TOKEN_UNAVAILABLE|The submitted device credential cannot be enrolled.|
|429|PAIRING_RATE_LIMIT|Too many pairing requests. Try again shortly.|
|429|INVITATION_LIMIT|Close an existing invitation or try again later.|
|503|PAIRING_UNAVAILABLE|Pairing is temporarily unavailable. Try again shortly.|

429 includes integer retryAfterSeconds1..3600 plus matching Retry-After header; the pending-count limit uses remaining oldest invitation TTL, not an invented hour. Invalid proof never reveals whether the UUID exists. Poll terminal expired/cancelled/access_denied statuses are200 because a valid verifier proved access; invalid proof is404. Feature disabled remains existing404; existing staff-auth gate may retain its established session response format before this route's operations run.

Rate accounting must survive rejection: public SQL entrypoints return an internal bounded `{ok:false,httpStatus,code,retryAfterSeconds?}` value after updating the fixed budget. The JS operation commits its transaction, then HTTP maps that result to the flat failure above. Never RAISE/throw for expected wrong proof, consumed invitation, rate rejection or expired state inside the transaction after charging budget: that would roll the counter back. Staff invite-limit rejections likewise commit charged owner counters. Unexpected infrastructure errors may roll back and return503. No raw SQL error/parameters are logged or returned. Independent-connection tests must prove rejected invalid-proof attempts consume the durable global budget.

Storage uses no append-only per-retry receipt table. Invitation row contains its original invite operationId+digest, one nullable approve operationId+digest+receipt, and one nullable cancel operationId+digest+receipt. First valid action fills its slot once. Exact replay returns that slot; changed digest409; fresh IDs against final state409 with no write growth. Uniqueness is owner/org+action+operationId over the fixed respective columns. Renewal stores only latest operationId/digest/receipt plus its expected-expiry fence on the existing worker. Invitation receipts expire with bounded24hour terminal retention; clients stop retrying expired enrollment and create a new UUID/secret rather than relying on permanent idempotency. Renewal receipt persists until the next successful renewal, and expectedExpiresAt prevents old operations from extending again afterward.

Suggested shared exports: workerDeviceStatus(pool,identity,org,{pairingId?,after?}); workerDeviceAction(pool,identity,org,input); workerPairingOperation(pool,action,proof,input). Public helper result contains transport status internally and is mapped only after COMMIT. SQL entrypoint names: app.worker_pairing_claim_v1(proof text,input jsonb), app.worker_pairing_poll_v1(proof text,input jsonb), app.worker_device_status_v1(pairing uuid,cursor jsonb), app.worker_device_action_v1(input jsonb). Helper/table names beyond these remain backend-owned implementation details. Backend owns migration220000, pure validators/HTTP/routes/DB tests; UI consumes the declared bare DTOs; Mac owns stdin/private files/fingerprint/exact replay. No service supervisor changes in this phase.
