# Telegram retained-source freshness

The connector checks retained messages in selected, unpaused chats with one read-only Telegram `GetMessages` request per source-work tick. It requests four message IDs in ascending order, then advances a durable per-chat cursor only after body changes, byte quota deltas, extraction invalidation and the page receipt commit together. At the end it resets the cursor and waits 60 seconds before cycling every retained ID again. History import, CV retrieval and source checks share a three-way round robin, with a control heartbeat between provider requests.

This is eventual reconciliation of retained records, not Telegram's native update feed. A `MessageEmpty` result clears retained text and attachments as **unavailable**; it does not establish why the message is missing. Inaccessible peers, omitted records, mismatched peers/IDs and provider failures defer without treating the source as deleted. Nothing proves that deletes before import, unretained messages or every historical edit were recovered. A large corpus can take many hours or days to cycle: at one connected tick per second, 200,000 records require at least 150,000 seconds (about 42 hours), plus normal history/CV work, cooldowns, retries, offline time and multiple selected chats. Timestamps describe completed checks and cycles, not a near-real-time guarantee. Native account/channel difference feeds with persisted provider state and explicit gap reconciliation remain the next scale/freshness improvement.

An encrypted account-scoped local pending page survives network uncertainty and restart. Replay uses the same page identity and records before another provider read. Server receipts are fenced by account, connection generation, chat version and selection/pause state. Flood waits apply account-wide cooldown. Quota rejection changes no source/cursor and exposes `CAPACITY_LIMIT`. Purged rows are never inserted by reconciliation.

Content or identity/attachment changes invalidate dependent extraction batches atomically. Their copied source text, proposals, evidence and attachment metadata are redacted; source digests rotate and leases close. Only affected machine facts lose support, preserving human fields, reviewed candidates and equal facts supported by other valid applied proposals. Timestamp-only changes do not invalidate facts. Invalidated snapshots keep non-content message references and a separate `source_invalidated_at`; actual raw disposal sets `source_purged_at` and frees quotas only when retained rows are removed.

Automatic refresh uses the existing extraction scheduler and worker. Each new immutable snapshot has at most 40 messages, normal 49KB packing or an existing bounded 327KB singleton. One active extraction batch per chat remains enforced by the existing unique index. Edits during a refresh rotate its digest and invalidate the result; pending refreshes resume through a new batch after the active job drains. Refreshes are fenced by current chat version, same-account connection generation, selection and extraction enablement. The existing bounded attempts, failed-job UI and explicit retry remain authoritative. Disabling extraction stops refresh; pause/deselection/reconnect fences old results and a later valid claim creates a fresh snapshot.

The unique source ledger survives raw deletion. `origin_job_id` is immutable disposal provenance; `job_id` tracks the latest retained-source extraction. Refresh cannot reassign or recover absent raw rows. Pending release or a purged origin prevents refresh. Original batch release still covers descendants: their draft review holds are included, active results are fenced, copied snapshots are redacted and reassigned raw rows are removed with exact quota accounting. Keeping a release-pending source reactivates eligible refresh work.

Staff freshness reads take 1–50 explicit chat UUIDs through `telegramSourceUpdateStatus(pool, identity, organizationId, chatIds)` and `telegram_source_updates_status_v1(uuid[])`. RLS enforces private owner scope. The result contains `chatId`, `mode`, `cursor`, `lastCheckedAt`, `lastCycleAt`, `nextCheckAt`, `errorCode`, `status`, `needsReextraction` and `sourceChangeReason`. `needsReextraction` remains true while source-derived facts need catch-up or retention/disabled extraction prevents it; completed checks alone do not mean AI catch-up completed.

The worker endpoint is `POST /api/telegram-source-updates/worker/{claim,complete,defer}`. It uses the existing bearer worker token and connection/account proof; browser-origin requests are rejected. No real Telegram credentials or accounts are needed for the offline SDK smoke, unit fixtures or disposable PostgreSQL runtime tests.
